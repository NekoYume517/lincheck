# lincheck 算法说明

本文记录实现中几个**不显然**的技术判断。它们都有对应的测试，但如果只看代码不容易理解为什么这样做。

## 1. WGL 搜索的候选条件

Wing-Gong-Lowe 算法的核心是判断「哪个操作可以成为全序中的下一个」。条件不是「它已经开始了」，而是：

```
op.start <= min(end of 所有尚未线性化的操作)
```

**为什么是 min(end) 而不是 min(start)**：一个操作只要还没完成，它就有可能排在候选操作前面。如果候选的 start 晚于某个未完成操作的 end，那两者不并发，候选必然在后，不能当"下一个"。

写错成「候选自己的 end 集合的最小值」会让剪枝完全失效：`register_bad` 会从 3 个搜索节点退化成 `3! = 6`，且漏掉 happens-before 约束，可能误判为线性一致。

## 2. 缓存键不能用哈希值

任务说明里写的是 `(hash(state), hash(remaining))`。实现时改成了**精确编码**：

```moonbit
// 不是这个
let key = (state_hash, set_hash)
// 而是这个
let key = "[1,2]|1011"      // 状态字面量 + 剩余集合的位串
```

**原因**：哈希碰撞会让搜索错误地相信某个子问题已经失败过，直接**漏报违规**。这是静默错误——不会崩溃，只会给出"线性一致"的假结论。代价是键变长（几百字节），但正确性不能赌。

## 3. 前缀和失败点必须原子记录

解释文本要说明"线性化到这里，然后某个操作无法解释"。最初 `best_depth` / `best_prefix` 和 `best_fail` 分开更新，结果出现前缀来自分支 A、失败原因来自分支 B 的错配——`stale_read` 会显示"前缀到 Write(1)，然后期望 → 0 但记录 → 1"，方向反了。

合并成一次 `record_progress(...)` 调用后修正。

## 4. 最小化必须加「可解释性约束」

这是本项目最重要的一条设计判断。

朴素 delta debugging 会这样压缩：

```
W=1 [0,10], W=2 [12,20], R->1 [30,40]
    ↓ 删掉 W=1
W=2 [12,20], R->1 [30,40]      仍然违规（读到 1，但只写过 2）
    ↓ 删掉 W=2
R->1 [30,40]                    仍然违规（初值是 0，读到 1 不可能）
```

最终得到单个 `R->1`。形式上仍是合法反例，但 bug 的性质变了：

- 原来是「读到**过期**值」——有并发、有覆盖，是真实的竞态
- 变成「读到**从没存在过**的值」——只需要检查初值就能发现，对调试毫无信息量

**约束**：若某操作单独看就违规，见证里必须存在一个同伴 `p`，使得 `{该操作, p}` 合法。判据只依赖 `Model` 和 `check`，四种模型通用，不碰模型内部。

实测效果：
- `register_bad`（3 个操作）：3 → 3，本来就最小
- `noisy_bad`（8 个操作，2 个真问题）：8 → 2，保留的是 `W=2 [12..20]` + `R->0 [22..24]`——正是"写先完成却读到旧值"

另留 `minimize_raw` 供纯 ddmin 对照，可以自己验证这个约束拦住了什么。

## 5. 生成器为什么能当元测试

`generate_consistent` 的做法：

```
1. 先在单一全序下顺序执行 N 个操作，记录每步的 (kind, result)
2. 为每个操作分配初始区间（顺序递增、不重叠）
3. 以 concurrency 概率随机"拉宽"区间，使相邻操作重叠
4. 拉宽时保持原全序关系：若 a 原本在 b 之前，拉宽后不能反转
```

因为产物**构造上**就来自一个合法全序，所以它必然线性一致。用它去测检查器：

- 若检查器报「违规」→ 假阳性，检查器有 bug
- 若检查器报「未知」→ 性能问题或剪枝有误

`selfcheck --seeds 300` 的结果：300 个合法历史全部通过，300 个注入违规全部检出。这是验证检查器本身正确性的核心手段——比写更多手工用例有效得多。

## 6. 超时返回 Unknown 而不是猜

搜索是 NP 难的。生产历史可能几十万操作，必然超预算。

三种结论严格区分：
- `Linearizable`——搜索穷尽，存在合法全序
- `Violation`——搜索穷尽，不存在
- `Unknown(reason)`——预算耗尽，**不知道**

把 `Unknown` 当成 `Linearizable` 是危险的（漏报违规）；当成 `Violation` 也是危险的（假警报）。所以必须保留第三态，让调用方决定怎么处理。

## 7. Int 是 32 位

集合模型用 64 位位图，但 `Int` 在 wasm 目标下是 32 位：

```moonbit
1 << 63     // → -2147483648，溢出
```

解决：状态编码成 `[低32位, 高32位]` 两个 Int，第 31..63 位都能正确表示。

同理，LCG 的 `state * 1103515245` 必须用 Int64 或及时 `& 0x7FFFFFFF`，否则溢出成负数。

## 8. 模型必须只排除物理上不可能的转换（审计发现）

对抗性审计发现 counter 模型把 `v == current` 的写入也拒绝了：

```moonbit
if v > current { Some(...) } else { None }   // 拒绝了原地踏步
```

这是把「单调计数器」过度收紧成了「严格递增」。对 set 语义的 API，写入
相同值在物理上完全可能（幂等写），拒绝它会让检查器对**行为正确的系统**
报出假违规——这是比漏报更容易让用户恐慌的失败模式，因为它指向一个
不存在的 bug。

修复为 `v >= current` 接受，只拒绝真正的回退。原则：

> 线性一致性检查器的模型应该**宽松到恰好排除物理不可能**的转换。
> 语义不确定时（increment-only 还是 set），选择宽松的一侧，并在模型
> 文档里写清楚假设。

顺带记录审计锁定的其他行为（`src/audit_test.mbt`）：

- `start > end` 的操作返回 `Unknown`（区间非法无法判定）而不是崩溃
- `apply` 不得原地修改传入状态——回溯正确性和缓存键都依赖这一点
- 缓存开/关在违规历史上结论一致
- 50ms 预算下 40 个全并发操作返回 `Unknown` 而不是挂死
- `Nil` 结果只在 `allow_unknown_results` 模式下可匹配，严格模式下是失配
- set 模型位图在 31/32/63 位边界正确（[低32, 高32] 编码）
- queue 两次 Pop 保持 FIFO
